## 👋 Introduction

**DevCase VB.NET Code Analysis** is a set of **Roslyn diagnostic rules** for Visual Basic .NET, most of them with an automatic **code fix** (Visual Studio lightbulb action). It finds and repairs problems that the built-in .NET analyzers do not cover for VB.NET: deadlock-prone `Await` expressions, silent guard clauses, missing or incomplete XML documentation, recursion, file-system loops that freeze the message pump, regular expressions without a ReDoS timeout, ambiguous dates, and much more.

Several rules are VB.NET equivalents of [**SonarQube**](https://docs.sonarsource.com/sonarqube-for-visual-studio/using/rules) rules, with an automatic fix that respects the semantics of the original code. Each rule document lists any overlap with Microsoft's built-in analyzers.

The whole project, analyzers, code fixes and tests included, is written in VB.NET with `Option Strict On`, `Option Explicit On` and `Option Infer Off`.

## 💡 Motivation

Over the years, I have established a rigorous custom coding standard for my VB.NET libraries: fail-fast argument validation, `ConfigureAwait(False)` on virtually every `Await`, comprehensive XML documentation covering absolutely every public and private member, mandating iterative methods over recursion, bit-shifted `<Flags>` enums to prevent manual integer calculation mistakes, explicit `Option` directives, etc. To enforce this discipline, I developed offline `VisualBasicSyntaxRewriter` snippets that I run across my codebases.

Although functional, that offline methodology is a tedious and time-consuming chore relegated to post-coding manual reviews, lacking any semantic context. **DevCase VB.NET Code Analysis** turns that standard into live diagnostics that show up while typing, with one-click fixes, and with semantic precision instead of text heuristics.

##### ⚡ The Real Question
Why keep fixing the same mistakes by hand when the compiler platform can point at them, and fix them, as you type?

## 🤖 Features

- **A comprehensive set of diagnostic rules**, most of them featuring a code fix, all fixes supporting **Fix All** (document, project and solution). Rules without a safe, behavior-preserving fix only report.
- **Semantic precision:** rules bind symbols through the Roslyn semantic model, so look-alike names (`myAsyncSettings.Result`) are not reported and no fix produces code that does not compile.
- **.NET Framework migration helpers:** dedicated rules prepare .NET Framework code for modern .NET by adding `#If NETCOREAPP` blocks with the recommended modern APIs, keeping the original code untouched in the `#Else` branch.
- **Behavior first:** when a fix offers several actions, the first one keeps the current behavior and only makes it explicit (for example `DateTimeKind.Unspecified` or `CultureInfo.CurrentCulture`); fixes that could change the result are never applied silently.
- **Respectful fixes:** preserve comments, trivia, region layout, line endings (CRLF/LF) and indentation; never reformat unrelated code.
- **Configurable** through `.editorconfig` (custom options and standard severity overrides).
- **Visual Studio 2022 and 2026** (amd64 and arm64) from a single VSIX.

## 📝 Requirements

- Visual Studio 2026 (18.x) or Visual Studio 2022 (17.8 or later), on Windows.
- The rules analyze Visual Basic projects that target any framework: .NET Framework, .NET Standard or modern .NET.

## 🚀 Getting Started

### Option A: Install the VSIX (recommended)

1. Navigate to the [Releases page](https://github.com/ElektroStudios/DevCase-VB.NET-Code-Analysis/releases/latest).
2. Download `DevCase.CodeAnalysis.Vsix.vsix`.
3. Close Visual Studio and double-click the `.vsix` file to install it.

### Option B: Build from source

1. Open `DevCase.CodeAnalysis.sln` in Visual Studio (workload: *Visual Studio extension development*).
2. Select the `Release` configuration and build `DevCase.CodeAnalysis.Vsix`, or run this command from the *Developer PowerShell for VS*:

   ```bash
   msbuild src\DevCase.CodeAnalysis.Vsix\DevCase.CodeAnalysis.Vsix.vbproj /restore /p:Configuration=Release
   ```

3. The package is generated at `src\DevCase.CodeAnalysis.Vsix\bin\Release\net472\DevCase.CodeAnalysis.Vsix.vsix`.

To debug the analyzers, set `DevCase.CodeAnalysis.Vsix` as the startup project and press **F5**: an experimental instance of Visual Studio starts with the extension loaded.

> [!NOTE]
> Analyzers installed through a VSIX run inside the IDE (live analysis, Error List and lightbulb), not on command-line builds. Info-level rules (DCA011, DCA013, DCA030, DCA031, DCA034, DCA042, DCA044, DCA048) appear in the *Messages* tab of the Error List and as gray dots under the code.

## ⚙️ Configuration

All the options are set in an `.editorconfig` file (or a global analyzer configuration file):

```ini
[*.vb]
# DCA010 (disabled by default because of legacy P/Invoke flag enums).
devcase_analyzers.dca010_enabled = true

# DCA001 code fix: emit ConfigureAwait(continueOnCapturedContext:=False).
devcase_analyzers.configure_await_named_argument = true

# DCA006 code fix: namespace used to wrap types declared in the global namespace.
# When not set: the namespace already declared in the file, or else the assembly name.
devcase_analyzers.default_namespace = Contoso.Tools

# DCA011 code fix: conditional compilation symbol of the throw-helper branch.
devcase_analyzers.dca011_condition = NET8_0_OR_GREATER

# DCA017 code fix: match timeout in milliseconds (default: 30000).
devcase_analyzers.dca017_timeout_ms = 30000

# Standard Roslyn severity overrides.
dotnet_diagnostic.DCA007.severity = suggestion
dotnet_diagnostic.DCA015.severity = none
```

## 🔕 Disabling rules

Every rule document has a **How to disable** section with ready-to-copy examples. In short:

```ini
# .editorconfig: one rule, or a whole category, for a solution, project or folder.
[*.vb]
dotnet_diagnostic.DCA022.severity = none
dotnet_analyzer_diagnostic.category-Performance.severity = suggestion
```

```vb
' A few lines of code.
#Disable Warning DCA024 ' Reason.
' ...
#Enable Warning DCA024
```

```vb
' A type or member (category and "ID:Title" as shown in each rule document).
<System.Diagnostics.CodeAnalysis.SuppressMessage("Design", "DCA024:Catch block only rethrows the exception", Justification:="Reason.")>
```

## 🧪 Quality

The test project (`xUnit v3`) builds in-memory VB.NET projects and:

- checks the **exact spans** of every expected diagnostic;
- applies every code fix repeatedly, re-parsing the text between passes like the IDE does, and verifies that the **fixed code still compiles**;
- verifies **Fix All** batch merging;
- runs every analyzer, code fix and Fix All test twice, with **LF and CRLF** line endings, and checks that the fixes never mix line endings (the Roslyn formatter writes the line ending of the operating system);
- compiles the .NET Framework rules against the real **.NET Framework 4.8 reference assemblies**, and the modern branch of their fixes against .NET;
- **enforces every DCA rule on its own code at build time**: the CodeFixes and Tests projects reference the analyzers as analyzers, the Analyzers project is checked by a self-analysis test, and Visual Studio's code style suggestions are raised to warnings in the repository `.editorconfig`, so the solution builds with 0 warnings;
- verifies that every suppression mechanism documented in the rules (`.editorconfig`, `#Disable Warning`, `SuppressMessage`) works;
- runs **all the analyzers on their own source code** (dogfooding) and checks that the code base contains no recursion.

```bash
dotnet test tests/DevCase.CodeAnalysis.Tests
```
